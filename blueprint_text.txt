UDO TECHNICAL IMPLEMENTATION BLUEPRINT
Admin App + Guest Experience System
1. Core architectural decision
Udo should be built as one platform with two delivery layers:
The first layer is the authenticated admin app for the couple, planner, and invited collaborators. This is the mobile product distributed through the App Store and Google Play. This app is where users plan, manage, configure, and monitor the wedding.
The second layer is the guest-facing web experience accessed through personalized links. Guests should not be required to create an account or install the app to RSVP, view updates, upload photos, access travel details, view the registry, or interact with the wedding experience. This guest layer should be a responsive mobile web application, though deep linking into the app can exist for invited collaborators.
This split is essential because it minimizes friction for guests while keeping the admin system powerful.
The product should therefore be thought of as:
Admin app = control layerGuest link = experience layer
The backend must support both layers from a single source of truth.
2. Recommended high-level stack
If your CTO wants the smoothest long-term path to Play Store and App Store quality, the cleanest architecture is:
Frontend admin app:
Flutter or React Native for cross-platform mobile 
Flutter is especially strong if you want one codebase and polished UI parity from Figma 
React Native is also fine if the team is stronger there 
Guest-facing web:
Next.js or a similar React-based SSR/ISR-capable framework 
This allows fast, SEO-friendly, mobile-optimized personalized guest pages 
If keeping one ecosystem matters, Flutter web is possible, but a traditional web stack will usually be better for guest links and email/web compatibility 
Backend:
Node.js with TypeScript using NestJS or Express 
Or Python with FastAPI if the team is stronger in Python 
Strong recommendation: TypeScript backend for consistency and schema safety 
Database:
PostgreSQL as primary relational database 
File/image storage:
AWS S3, Cloudflare R2, or Supabase Storage 
Realtime/eventing:
WebSockets or Pusher/Ably for live updates 
Background job queue for reminders, send events, and workflow triggers 
Redis for queueing, caching, and ephemeral state 
Messaging/integrations:
Twilio for SMS / WhatsApp 
SendGrid / Postmark / Resend for email 
Stripe for registry contributions 
Pinterest API for inspiration ingestion 
Google Maps / Places for maps, directions, hotels, and venue proximity 
Calendar export via ICS generation 
Push notifications via Firebase Cloud Messaging / Apple Push Notification Service for authenticated app users 
Authentication:
Admin app: email/password + social auth optional 
Guest link: tokenized access, no forced login 
Collaborators: authenticated app users with scoped roles 
If your CTO prefers one-service simplicity and fast iteration, Supabase is also a realistic option for:
Postgres 
Auth 
Storage 
Realtime 
Edge functionsBut for long-term control, a custom backend is stronger.

4. User roles and permission model
The permission model must be explicit from the start.
Core roles
Owner / Primary Couple UserFull control of wedding data, settings, billing, guest management, messaging, registry, gallery, and collaborator access.
Partner / Co-ownerNear-full access, depending on configuration.
PlannerOperational access to planning, guests, logistics, invitations, messaging, live operations, and possibly registry/galleries depending on client preferences.
CollaboratorScoped access to selected modules, such as:
viewing timelines 
helping with guest logistics 
moderating uploads 
sending wedding party communications 
GuestNo app admin access. Uses personalized link only.
Permission domains
Permissions should be domain-based, not page-based. Suggested permission groups:
manage_plan 
manage_guests 
manage_invitations 
manage_guest_experience 
manage_messages 
manage_live 
manage_gallery 
manage_registry 
manage_logistics 
manage_collaborators 
view_financials 
This avoids hardcoding access around screens and allows flexible collaboration models.

registry reminder → goes through Messages

16. Tokenized guest access design
Guest links should be secure but frictionless.
Recommended model
Each guest gets a signed access token or opaque token referencing:
wedding id 
guest id 
role/view type 
expiration / revocation metadata 
This token should not expose internal IDs directly.
Requirements
revocable by admin 
regeneratable if needed 
optionally one general wedding link plus guest-specific personalized links 
rate-limited and abuse-protected

19. App Store and Play Store implementation considerations
Must-have product polish
smooth auth and onboarding 
deep links from email/SMS/WhatsApp into app or guest web 
excellent loading states 
no broken image placeholders

20. Suggested AI coding workflow for CTO
If your CTO wants to use AI effectively, the best workflow is:
First, feed AI the design system and page ownership rules.Second, feed AI the data models and route structure.Third, feed AI a single module at a time with:
owning page 
states 
required interactions 
backend endpoints 
event triggers 
Do not ask AI to build the whole app in one go. It will blur responsibilities.
A better order is:
auth + wedding shell 
Home summaries 
Plan core models 
Guests core models 
Guest List + Drawer 
Invitations

Messages 
Logistics 
Live
