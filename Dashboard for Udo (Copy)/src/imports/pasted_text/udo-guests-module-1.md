MASTER FIGMA PROMPT — UDO GUESTS MODULE (FULL PRODUCTION SYSTEM, FULLY MERGED)

Design and fully build the Guests module of Udo as a complete, production-ready subsystem inside a premium wedding planning platform. This must not feel like a loose collection of screens. It must feel like a calm operating system for guest management, communication, experience, and logistics. The entire module should reduce stress, eliminate ambiguity, and help the user feel that nothing is slipping through the cracks. The design language must align with the rest of Udo: soft, modern, premium, editorial, emotionally intelligent, and highly legible. Nothing should feel corporate, flat, overstuffed, childish, or unfinished. The module must feel like it was designed by someone who understands both wedding emotions and operational complexity. Every screen must clearly tell the user what it is for, what matters most, and what they can do next.

Use a mobile-first design system with a warm, refined palette. The primary background should be a soft warm ivory or off-white. Elevated cards should be white or lightly blush-tinted. The primary action color should be a deep elegant green used for active states, confirmations, and important actions. The secondary accent should be a muted dusty rose used for edit actions, highlights, alerts, and softer CTAs. Secondary background tones can include pale blush, champagne neutral, and warm taupe dividers. Typography must use a refined serif for page titles and emotionally resonant section headers, and a clean sans-serif for all functional elements, labels, chips, inputs, buttons, tables, and status badges. Use rounded cards with subtle shadows, generous padding, and deliberate spacing. Every major section should feel clearly grouped and breathable. Use an 8pt spacing system. Mobile frame should be built around 390 x 844 and desktop preview frames may also be created where helpful. All layouts must use auto layout and reusable components.

This module must work within a larger product architecture where admins use the app and guests use a personalized link. Guests should not see the backend app navigation by default. The Guests module in the app must control everything guest-facing, but the actual guest experience should be rendered as a mobile-optimized guest link or wedding microsite. The builder inside the app must therefore always have a preview function that shows what the guest will actually see when they open the invitation link. The guest-facing experience must include RSVP, schedule, travel, messages, gallery, and live updates as one continuous flow, not as separate app tabs. Collaborators such as planners, partners, or certain wedding party members may have limited app access, but regular guests should interact primarily through the link.

Every single button, arrow, chip, card, toggle, and clickable row must lead somewhere real. There must be no placeholders, no dead buttons, no “coming soon,” and no non-functional UI. If a button says “Edit,” create the edit panel. If a button says “Preview,” create the preview state. If a button says “Send reminder,” create the pre-filled reminder modal and success state. If a row opens a detail page, create that detail page in full. If a publish action exists, create the confirmation state. The build must feel like a real product, not a visual concept.

The top-level Guests module should contain these six primary tabs in this exact order: Overview, Guest List, Invitations, Guest Experience, Messages, and Guest Logistics. These tabs must all be fully designed, fully connected, and clearly distinct in responsibility. In addition, several advanced pages and subpages must exist within this module, launched from these tabs rather than becoming redundant new tabs. These advanced pages include Guest Insights, Guest Journey, Communication Center or advanced messaging views, VIP / Priority Guests, and Experience Design. Seating must remain owned by the Plan section of the product. The Guests module may show seating status, seating completeness, or allow a quick assignment or shortcut into the seating planner, but it must not duplicate the entire seating builder inside Guests.

PAGE 1 — GUESTS OVERVIEW

This page should feel like a control tower and a deep exhale. The user should land here and immediately feel that they understand the big picture. This page must answer three questions without effort: how are my guests progressing, what needs attention, and what should I do next. The visual tone should be calm and reassuring, not analytical or severe. The page should feel supportive and intelligent, as though the system is helping the user think clearly.

At the top of the page, create a refined header block with the page title Guests in a premium serif. Directly beneath the title, add a line of soft secondary context text that reads exactly: “120 guests · RSVP deadline June 1 (12 days left)”. Beneath that, add a small, gentle line of encouraging copy such as: “You’re doing beautifully — let’s look at what matters next.” This line should be understated, muted, and elegant, not loud or overly sentimental. It is there to reduce anxiety and establish tone.

Below the header, create a 2x2 grid of summary cards. These cards must feel like soft, clickable signals rather than hard metrics. The cards should be labeled Total Guests, Confirmed, Awaiting RSVP, and Incomplete Guests. The old “Needs Attention” wording should be removed and replaced with “Incomplete Guests” to eliminate ambiguity. Each card must include a large number, the card title, and a one-line explanation. Total Guests should say “Everyone invited so far.” Confirmed should say “Guests who have RSVP’d yes.” Awaiting RSVP should say “Guests who haven’t responded yet.” Incomplete Guests should say “Missing meal, travel, or key details.” Each card must be clickable and lead into the Guest List page with the correct filter applied. Total Guests opens all guests, Confirmed opens attending guests, Awaiting RSVP opens pending guests, and Incomplete Guests opens a filtered view for guests missing critical information. The cards should use subtle colour cues only where helpful: green for confirmed, muted rose for pending or incomplete, neutral tones for total.

Below the summary cards, create a full-width section titled Guest Progress. This replaces the old “Guest Readiness” concept. This section should feel like a soft diagnostic layer rather than a performance report. Include four progress rows labeled RSVPs received, Meals selected, Travel details added, and Seating assigned. Each row should have a label on the left, a gently rounded progress bar in the center, and a value such as 82 / 120 on the right. The progress bars should use soft green for strong completion, neutral tones for mid-range completion, and muted rose when progress is meaningfully behind. Under the set of bars, include a reassuring sentence that reads: “You are making great progress. Most guests have responded, and key details are coming together.” Each progress row must be clickable and open the appropriate filtered view. RSVP completion should open pending or completed RSVP views. Meals selected should open guests missing meal selections. Travel details should open Guest Logistics filtered to guests missing travel fields. Seating assigned should open a filtered view or a shortcut into Plan’s seating builder.

Below Guest Progress, add a card titled What to focus on next. This section should behave as the module’s intelligence layer and should feel like a calm nudge rather than a command. The body text should say something like: “You are doing well. A few guests still need to respond, and some meal details are missing. This is a good time to follow up and complete those details.” Under this text, add 2 or 3 buttons: View pending guests, Review guest details, and, if relevant, Review seating. Each button must work and navigate correctly. Keep the tone gentle and helpful.

Directly beneath that, add a section titled Take action. This section is critical because it bridges awareness and execution. It should contain a small set of well-spaced action buttons or cards such as Send RSVP reminders, View pending responses, Complete guest details, and Assign seating. These actions must lead to real modals or pages, not just route changes. For example, Send RSVP reminders should open the Messages reminder flow pre-filled with pending guests. Complete guest details should open the Guest List filtered to missing data. Assign seating should open or hand off into the seating planner in the Plan tab.

Add a lightweight section titled Guest Groups that displays simple segmentation counts like Wedding Party and Travelling Guests. This section should be visually minimal and not compete with the core control elements. It is simply there to reinforce structure. Clicking these should filter the Guest List accordingly.

Add a What’s already come together or Wins this month style section lower on the page to preserve emotional warmth. This should not feel gimmicky. It can say things like “82 guests have RSVP’d — your day is taking shape beautifully.” If there is less progress, it should say “Every step you take here brings clarity — you’re exactly where you need to be.” This section is important because it aligns with the brand idea that Udo means peace and should make the user feel held, not just managed.

At the bottom, include a refined Recent Activity card. Do not use low-value activity like “opened link” if it creates noise. Keep only meaningful items such as new RSVP responses, missing meal selections surfaced, or newly added guests. Each row should be brief and decision-relevant. The old “Preview guest views” section should not live here. It should move to Invitations or Guest Experience, where it is more contextually relevant. These changes sharpen the hierarchy and turn the page into a useful guide rather than a loose dashboard.

From this Overview page, add entry points into two advanced supporting pages: Guest Insights and Guest Journey. These should be secondary navigation buttons or deeper cards, not top-level tabs. Guest Insights should analyze guest mix, behavior, travel burden, and cluster patterns. Guest Journey should show where each guest is in the overall lifecycle: invite sent, RSVP completed, travel added, stay assigned, event ready, post-wedding follow-up. These are not “nice-to-haves”; they turn guest data into intelligence. Their detailed structure appears further below.

PAGE 2 — GUEST LIST

The Guest List page must function as the operational core of the module. It should feel like a clean, intelligent CRM for wedding guests, not like a spreadsheet. This page is for speed, scanning, and fast intervention. It should not be overloaded with insights, logistics dashboards, or emotional fluff. The user should be able to arrive here and instantly understand: who these guests are, what their status is, and what needs to be updated quickly.

At the top, include a clear title Guest List and a subtitle that says: “View, filter, and manage every guest in your wedding plan.” At the top right or in the action bar, include buttons for Add or Invite Guest, Import Guests, and Export List. Below the action buttons, place a search field with the placeholder: “Search by name, email, phone, tag, or missing detail.” Include a subtle quick-add icon or shortcut inside the search area so the user can add someone rapidly without losing flow.

The filtering system needs to be carefully structured to avoid confusion. Use a primary row of chips for RSVP status: All, Attending, Pending, and Declined. Then use a secondary dropdown or segmented control for category filters such as Travelling, Missing details, Family, Friends, Wedding party, and VIP if that concept is used. Make the filter state clearly visible once applied, for example as a small active chip at the top that reads Filtered by: Missing details.

Each guest row should be a clean horizontal card, not a dense table row. On the left, show the guest’s name in bold and their email beneath it in muted grey. Include phone if available. In the center, show a concise cluster of status indicators: RSVP status badge, meal icon or badge, travel icon if applicable, and plus one indicator. If useful, show up to two tags such as Family or Vegetarian, but do not overload the row. On the right, show small quick action icons such as Send reminder, Edit, and More, plus a chevron or arrow indicating the guest can be opened. Rows for guests with missing information should have a very soft tinted alert background, such as pale rose, so missing details are visible at a glance without becoming visually noisy.

Clicking a guest row must open a Guest Detail Drawer or side panel rather than requiring a full hard navigation unless mobile constraints make a separate detail page more appropriate. This Guest Detail interface is one of the most important screens in the entire system and must include the following sections: Basic Details, RSVP & Attendance, Meals, Travel & Stay, Access & Visibility, Invite History, Notes, and Tags. Basic Details should include name, email, phone, and guest group. RSVP & Attendance should include attending / pending / declined status, plus one count, and date of response. Meals should include dietary preference, selected meal, allergies, and notes. Travel & Stay should include whether the guest is travelling, arrival date and time, departure date and time, airport, hotel, transport need, and notes. Access & Visibility should show which private or public guest-facing sections and events this guest can see, especially if they are in the wedding party or are a travelling guest. Invite History should show when the invite was sent, through which channel, whether it was opened, and whether reminders were sent. At the bottom, include action buttons such as Send message, Send invite link, Assign hotel, Assign transport, Mark manually, and Remove guest. Every one of these must work.

Bulk actions must exist. When the user selects multiple guests, a sticky bottom action bar should appear allowing Send reminder, Add tag, Assign hotel, Assign transport, Mark RSVP manually, Request details, and Export selected. This is necessary for real operational use at scale.

The Add or Invite Guest flow must support two clear paths: Quick Invite and Manual Add. This should be either a modal or small decision screen. Quick Invite should allow entering just enough data to send a personalized link — name, phone or email, tag, and preferred send method. Manual Add should allow entering the person fully, including RSVP, plus one, meal, travel, and notes for older relatives or people who will not self-serve. Add subtle helper copy that reminds the user they can still send the guest their own link later if they want the guest to complete their own information. This solves the problem of over-manualizing the guest onboarding flow.

This page should not include heavy insights, travel dashboards, or engagement mechanics. Those belong elsewhere. Its job is operational clarity. Anything that does not support fast management should be moved out. The page should feel like “I can manage 200 guests here without stress.” It should be one of the sharpest execution surfaces in the entire app.

PAGE 3 — INVITATIONS

The Invitations page must feel like a guided system that moves the user through a clear flow: build → send → track. It should be emotionally resonant because this is the first moment the guest “feels” the wedding, but it must also be operational because the user needs to send at scale and monitor responses. The page should not feel like a loose cluster of cards. It should feel like one obvious workflow.

At the top, create the title Invitations and a subtitle such as: “Preview, send, and track invitations in one place.” The first and most prominent section should be Your Invitation. Replace any vague “Invitation Preview” language with this. The preview itself should be a large, beautiful card with couple names, date, location, optional invitation text, and a clear sense of the chosen style. It should feel like a premium mobile invitation, not like a generic graphic. Underneath the preview, include three clear buttons: Edit Content, Change Theme, and Preview Experience. Edit Content opens a panel or page where the user can change names, date, venue, message, quote, dress code snippet, RSVP deadline, cover image, and other invitation text. Change Theme opens a curated theme selector with options like Classic Ivory, Soft Rose, Botanical Green, Modern Minimal, Champagne Neutral, and Evening Black Tie. Avoid unlimited customization; keep it curated so the result stays premium. Preview Experience must open a full-screen preview of what the guest sees when they click the invitation link, not just the card itself. This is crucial because the product’s value is not the invitation card alone, but the full guest experience link it unlocks.

Below that, create the Send Invitations section. Include a soft intelligence banner that says something like “22 guests have not received an invitation yet” with a button Send now. Below this, present delivery methods as clear channel cards, not generic buttons. Use cards for Email, SMS, WhatsApp, and Copy Link. Email should indicate how many guests it will reach. SMS should mention speed and visibility. WhatsApp should be highlighted slightly because it is likely a high-engagement channel. Copy Link should be framed as a manual share option. Clicking any method must open a full modal or flow that allows recipient selection, message editing, preview, and sending or scheduling. Each send flow should support a send-now and schedule-later path.

The bottom section of this page should be Invitation Performance. This should include metrics like sent, delivered, opened, responded, bounced, and pending. Above these metrics, add a brief interpretation sentence such as “Your open rate is strong, but 22 guests have not responded yet.” Below the metrics, include a lightweight recent activity list showing meaningful items like guest opened invite, guest responded yes, or delivery failed due to missing number. Also include an action button Send reminder to pending guests that opens the Messages reminder flow. This page should make it obvious: this is my invitation, these are my channels, and this is how it is performing.

PAGE 4 — GUEST EXPERIENCE BUILDER

This is one of the most important parts of the product and currently the most structurally vulnerable. It must be reframed as a builder and not as a dump of settings. The page should feel like: “I am shaping how my guests will experience the wedding.” It should not feel like a settings page.

At the top of the page, create a large, visually dominant section called Guest Experience Preview. This preview must be the anchor of the page. It should show a realistic mobile wedding webpage inside a device-like frame or polished card container. At the top of the preview area, include toggles for Mobile / Web and Attending Guest / Travelling Guest / Wedding Party / Pending Guest. Switching these must update the preview instantly. The preview itself must show the actual guest-facing page, including a hero card with names, date, location, action buttons like Add to Calendar, Open in Maps, and View Schedule, and the conditional sections the user has enabled, such as Events, Dress Code, Travel & Stay, Gallery, Message Board, and Live Updates. The preview must not be fake or static; it must visibly react to changes made elsewhere on the builder.

Below the preview, structure the builder into clearly labeled modules. The first should be What Guests Will See. Inside this module, create grouped cards for Event Information, Visual Experience, Interaction, and Travel & Stay. Event Information controls toggles like Show Schedule, Show Venue Map, and Show Dress Code. Visual Experience controls Show Couple Photo, Show Wedding Story, and Enable Gallery Uploads. Interaction controls Enable RSVP, Enable Message Board, and Enable Live Updates Popup. Travel & Stay controls Show Nearby Hotels, Show Transport Details, Show Flight Guidance, and Show Travel Notes. Every row should include the label, a one-line explanation, and a toggle. When a toggle changes, the preview must update instantly.

The next module should be Guest Access Rules. This controls who sees what. Present this as a set of rows with an event or section name, its current visibility, and an arrow. Clicking the row opens a modal called Edit Access where the user can select All Guests, Wedding Party, Family, Travelling Guests, or Custom Tags. Saving this must update both the label and the preview. This is where things like wedding party-only rehearsal details or travelling guest-only logistics appear. This is critical for a wedding where different groups need different visibility.

The third major module is Live Updates. This should not feel like a separate tab inside this builder; it is a control for real-time updates that appear in the guest experience. Add a button + Create Update. Clicking it opens a modal with title, message body, audience selector, and delivery methods such as Push to Guest Page (popup), SMS, WhatsApp, and Email. If the guest currently has the page open, the update should appear as a popup overlay in the preview simulation. If they do not, the update should be stored in their updates feed. This page must make the relationship between planner-side actions and guest-side effects completely clear.

At the bottom, include Preview full guest page, Copy guest link, and Publish updates. All must work and show proper confirmation states. The publish confirmation should say something like “Guest experience updated successfully.” The emotional tone across this page should include subtle guidance, like: “This is what your guests will see when they open their invitation link.” It should feel like the planner is shaping an experience, not toggling a system.

As part of Guest Experience, also include supporting pages for Website Structure Editor and Theme Selector if not already embedded. The structure editor should let the user show or hide modules like Welcome, Story, Schedule, Travel, Dress Code, Registry, FAQ, Message Board, and Gallery. It should allow reordering. The Theme Selector should offer curated visual themes and font pairings and update the live preview instantly. This is especially important because the user does not want guests limited to green and pink only; they need curated tasteful theme alternatives.

PAGE 5 — MESSAGES

The Messages page must evolve into a Communication Center. It should not feel like a passive inbox. It should feel like a place where the user can target, time, and send communication without chaos. The page should answer: who needs to hear from me, what should I send, and how is communication performing?

At the top, create a strong action row with Compose Message, Send Reminder, and View Message History. Compose opens a full-screen or large modal message builder. Send Reminder opens a targeted reminder flow. View History opens a list of previously sent communications.

Immediately below, create a section called Smart Alerts. This should surface communication-relevant issues such as 18 guests have not RSVP’d, 12 travelling guests are missing hotel details, or 7 guests are missing meal choices. Each alert should be a full-width or medium card showing the problem, a short explanation, and a CTA like Send RSVP Reminder, Send Travel Info Request, or Request Meal Choices. Clicking the CTA must open the message composer with the correct audience, suggested channel, and pre-filled message template. This is essential because it turns the page from a messaging page into a communication intelligence layer.

Below Smart Alerts, add an Audience Targeting section with chips for All Guests, Pending RSVP, Wedding Party, Travelling Guests, Family, Friends, VIP, and Custom Tags. Selecting one or more chips should update the message composer context. The page should clearly show which audience is selected and how many recipients are included. For example, the compose panel can say: “You are about to message 18 pending guests.”

The Compose Message experience must be designed in full. It should include audience, channel selector (Email, SMS, WhatsApp, Guest Page Popup), message type (Message, Reminder, Live Update), optional subject, message body, attachments, and preview. Add smart attachments rather than turning messaging into a freeform chat app. Smart attachments should include image, location, document, and link. If the audience is Travelling Guests, the system should suggest hotel links or travel notes. If the message is a Live Update, it should also show how it appears on the guest page as a popup. At the bottom of the composer, include Send now, Save draft, and Send test to self. All must work. This is important because the user asked whether uploads should be supported — yes, but as structured attachments, not as chaotic messaging uploads.

Lower on the page, create Messages from Guests. This is the emotional layer. Show cards with guest name, message snippet, and timestamp. Clicking a card opens a lightweight thread view with message history and a reply field. This section should feel warm, not transactional, because it reflects real notes and responses from guests. It is a nice counterbalance to the operational messaging surfaces.

As an advanced supporting page under Messages, include a deeper Communication Center or Message Performance screen if needed. This should track sent messages, open rates, response rates, scheduled campaigns, and recurring reminder sequences. It should allow the user to think strategically about communication, not just send one-off messages. This fulfills the earlier concept of turning messaging into a communication system rather than a feature.

PAGE 6 — GUEST LOGISTICS

This page must act as a command center, not a dashboard. Its purpose is to answer: which guests are at risk of having a bad arrival or stay experience, and how do I fix it now? It should be one of the strongest differentiators in the product because most wedding tools do not handle guest logistics deeply or gracefully. Both uploaded logistics prompts emphasized problem-first thinking, prioritization, and action immediacy, and this page must reflect that.

At the top, create a section called Logistics Action Center with a soft rose background. This should immediately surface what is broken. Use horizontally scrollable or grid-based alert cards. Examples should include 8 guests arriving in 72 hours without transport, 14 guests have no hotel assigned, and 6 guests are missing flight details. Each card should include an icon, a title, a short explanation of why it matters, and a green CTA button such as Assign transport, Assign hotels, or Request details. Clicking the body of the card should filter the Guest Logistics work area. Clicking the CTA should open a targeted modal with the affected guests preselected.

Below that, create a Logistics Overview section with KPI cards focused on problems rather than totals. Use cards for Flights Missing, Hotels Not Assigned, Transport Not Assigned, and Fully Ready Guests. Each card must be clickable and filter the relevant guest set. This is a problem dashboard, not a vanity metric area.

Below that, add a Travel Readiness tracker card that contains clickable progress rows for Arrival Dates Collected, Departure Dates Collected, Flights Added, Hotels Assigned, and Transport Assigned. Each row should show a label, a progress bar, and a current / total value. Color logic should be used carefully: green for strong completion, neutral for moderate progress, and rose for low completion. Clicking a row filters the guests needing that specific information.

The largest and most important work area should be Guests Requiring Attention. This list should be grouped into Urgent, Missing Key Info, and Partial Completion. Urgent includes guests arriving soon who are missing any critical logistics fields. Missing Key Info includes guests missing flight, hotel, or transport. Partial Completion includes guests with some but not all data complete. Each guest card should show avatar or initials, name, origin or airport, arrival date, hotel status, transport status, and a clear status badge. Each card must include action buttons such as Request Info, Assign Hotel, and Arrange Transport. Clicking the card opens a Guest Logistics Detail Drawer showing all travel and stay details, editable fields, and messaging shortcuts. Clicking Request Info opens a pre-filled message modal. Clicking Assign Hotel opens the hotel selection modal. Clicking Arrange Transport opens a transport assignment modal.

Below that, include separate management cards for Hotel & Stay Setup and Transport Setup. Hotel & Stay Setup should show how many hotels are selected and how many guests remain unassigned, with a CTA Assign hotels to guests that opens a hotel selector with multi-select guest assignment. Transport Setup should show guests needing transport and current vehicle or seat capacity, with a CTA Edit transport plan that opens the shuttle builder or transport configuration modal.

Add optional but powerful Smart Suggestions on this page, such as “5 guests arriving at the same time — group transport?” or “3 guests booked the same hotel — consider one shuttle.” These suggestions should feel like gentle intelligence, not overwhelming AI. Bulk actions must also exist here: if the user selects multiple guests, a sticky bottom bar should appear with Send Message, Assign Hotel, and Assign Transport. The page must make one thing true: if something is broken, the user can see it and fix it in one or two taps.

ADVANCED SUPPORTING PAGE — GUEST INSIGHTS

This page should live as an advanced layer accessible from Overview or More within the Guests module. It must not clutter the main tabs, but it is too valuable to omit. Its purpose is to transform guest data into planning insight. It should analyze guest composition, travel burden, social clusters, and behavior patterns, then surface recommendations. This is where the product starts to feel like a thinking system. It should include a summary header with insights like “62% of your guests are travelling”, “18 guests are travelling internationally”, or “Most guests respond within 48 hours.” Each insight should have a short explanation and a CTA to the relevant page. Include composition charts for Family vs Friends vs Colleagues and Local vs Travelling vs International. Add a Travel Burden analysis card highlighting long-haul or same-day arrival risks. Add Social Clusters showing natural guest groups, which feed into seating and messaging. Add Behavior Patterns showing early responders, late responders, and non-responders. This page is strategic and should feel calm, analytical, and powerful, not busy.

ADVANCED SUPPORTING PAGE — GUEST JOURNEY

This page should map the full lifecycle of each guest from invite through arrival and participation. It should show a horizontal or staged journey such as Invite → RSVP → Flight → Hotel → Transport → Event → Post-wedding. At the top, include an overall journey progress summary. Below that, show individual guest journey rows with completion indicators at each stage. Clicking a guest should open their detail drawer with the relevant part of the journey highlighted. Also include a Bottleneck Analysis section that shows where most guests are getting stuck, such as hotel selection or travel details, and provide CTA buttons to fix those drop-offs. Add Journey Automations such as RSVP reminder sequences or travel reminder flows. This page turns the guest experience into a process the planner can actually manage.

ADVANCED SUPPORTING PAGE — VIP / PRIORITY GUESTS

Create a page or special filtered mode for VIP or Priority Guests. This is especially useful for luxury weddings or weddings where certain people require extra coordination. Show a clear list of VIPs such as parents, core family, or wedding party leaders. Each VIP card should surface travel readiness, seating importance, communication history, and any special notes. Include actions such as Send Personal Message, Assign Priority Seating, Confirm Arrival, or Add Special Instructions. This page should feel calm and elevated, like “special handling” rather than “problem management.”

ADVANCED SUPPORTING PAGE — EXPERIENCE DESIGN

This page extends Guest Experience into an emotional planning layer. It should help the planner think not only about what guests need, but how they should feel. Include sections like Welcome Experience, Event Personalization, Gift or Welcome Notes, Preference Collection, and Emotional Moments. For example, a travelling guest could see a more hospitality-forward experience, while a wedding party member could see a more insider schedule. This page is where experience becomes curated rather than merely configured. It should connect directly to the Guest Experience builder and the guest-facing preview.

GUEST-FACING LINK PREVIEW RULE

Across Invitations, Guest Experience, and Live Updates, the guest-facing link must always be previewable as a real mobile web page. This preview must not be a placeholder. It should show the landing page, hero section, RSVP card if incomplete, event schedule, travel details, messages, gallery, and live updates in one unified wedding microsite. Depending on guest type, different blocks should appear or disappear. For example, Pending Guests should see RSVP as primary. Travelling Guests should see hotels, transport, airport, and maps. Wedding Party should see rehearsal details and call times. Attending Guests should see the full schedule and relevant guest information. Live Updates should appear as popups if the page is open and as feed items or badges if it is not. This guest-facing preview is crucial because it communicates to the CTO and designer exactly what the outputs of the planner’s configuration look like.

GLOBAL BUTTON AND STATE RULE

No visible control may be non-functional. If a button exists, build its destination. If a toggle exists, define what changes. If a modal has Save, define the saved state. If a Send action exists, define confirmation. If a Copy action exists, show a copied toast. If a Publish action exists, show a publish confirmation. If a section is filterable, show the active filter state. If a page has no data, create a calm, purposeful empty state that tells the user what to do next. This applies across all pages. This is non-negotiable.

FINAL EXPERIENCE TARGET

When complete, the Guests module should make the user feel:
“This is not just a guest list. This is guest control, guest communication, guest logistics, and guest experience — all working together beautifully.”

It should reduce stress. It should reduce chasing. It should reduce ambiguity. It should help the user think. It should feel like peace, structured.
