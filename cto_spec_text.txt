UDO APP: CTO SYSTEM SPECIFICATION
Core App Architecture, Page Responsibilities, Data Flows, and Product Logic
1. Product Positioning and Architectural Principle
Udo is not just a wedding planning app. It should be built as a calm operating system for weddings, where the user experiences a guided flow from planning to coordination to execution to memory-keeping. The product must feel emotionally intelligent, but the underlying system must be extremely clear and modular.
There are two distinct experience layers in the product:
A. Admin / Planner App Experience
This is the actual mobile app used by:
the couple 
the planner 
optionally trusted collaborators such as maid of honor, best man, family organizers 
This is where the user:
plans 
configures 
tracks 
sends 
updates 
manages 
B. Guest Experience Layer
Guests should not be forced into the app by default. Their primary experience should be through a personalized link-based guest web experience, which can optionally open in-app if they are invited to collaborate or explicitly choose to install. This guest link acts like a wedding microsite personalized by guest role and status.
The key rule is:
The app is for control. The link is for experience.
That means the app pages below are primarily admin pages, but they must all contribute to the final guest-facing experience.
2. Primary Navigation and Role of Each Page
The bottom-level app navigation should remain:
Home 
Plan 
Guests 
Live 
Gallery 
More 
Each top-level page has a distinct purpose and must not become a dumping ground for other systems.
Home
The calm command center. This is the summary page and guidance layer.
Plan
The structured planning engine. This owns tasks, checklists, budgeting, timelines, seating, vendors, and plan-level configuration.
Guests
The guest operating system. This owns guest records, invitations, guest communication, guest experience settings, and guest logistics.
Live
The wedding week and wedding-day reassurance and coordination layer. This should be dual-mode internally: calming bride/couple view and operational planner/backend view.
Gallery
The inspiration + memory + upload ecosystem. This owns inspiration boards, moments timeline, guest uploads, favorites, and archive.
More
Secondary settings, preferences, account, billing, support, integrations, etc.
3. Global System Rules
Rule 1: One Source of Truth Per Function
Every feature must have a single owner page. Derived views may appear elsewhere, but editing ownership must be clear.
Examples:
Seating is owned by Plan, not Guests. 
Guest records are owned by Guests, not Plan. 
The guest-facing website structure is owned by Guests → Guest Experience, not Home. 
Registry is a standalone module, but distribution is controlled from Invitations and Guest Experience. 
Rule 2: Derived Views Can Appear Elsewhere
A page may show summary data from another module, but not duplicate its full logic.
Examples:
Home can show “seating progress,” but seating editor belongs in Plan. 
Live can show “most guests arrived,” but guest arrivals logic is fed from Guests / Logistics. 
Guests can show “seating assigned” as a field, but not a full seating planner. 
Rule 3: No Dead Screens
Every button, card, badge, filter, and CTA must either:
navigate to another page 
open a modal/drawer 
update state visibly 
apply filters 
trigger a real action 
Rule 4: Calm UX on the Surface, Structured Logic Underneath
The user experience should feel soft and guided, but the backend should be explicit, rule-based, and deterministic.
Rule 5: Role-Based Experience
The app should support role-based rendering and permissions:
Owner / Bride / Groom 
Planner 
Collaborator 
Wedding party collaborator (optional scoped access) 
Guest (primarily link-based) 
Guests should not see admin pages.

5. Home Page — CTO Specification
Purpose
Home is the emotional control center and summary layer. It should not own planning logic, guest logic, or deep editing. It should synthesize them.
What Home should do
Home should answer:
Where are we overall? 
What matters now? 
What is on track? 
What needs attention this week? 
Core sections Home should contain
countdown to wedding 
progress / readiness summary 
“What to focus on next” 
recent milestone wins 
RSVP progress summary 
budget snapshot 
latest guest activity 
quick actions 
emotional reassurance / tone-setting 
shortcut into crisis / support if needed 
Data Home consumes
Home reads from:
Wedding 
Plan tasks / deadlines 
Guest completion metrics 
Invitation progress 
Logistics completion 
Registry progress 
Live state for final days 
Data Home should not own
Home should not own:
actual task editing logic 
seating builder 
guest record editing 
invitation builder 
logistics assignment 
gallery moderation 
Interactions from Home
Every major card on Home should deep link into the owning module.
Examples:
“12 guests pending RSVP” → Guests with Pending filter 
“Budget needs attention” → Plan → Budget subsection 
“3 transport items incomplete” → Guests → Guest Logistics 
“Registry not published” → Registry module 
Final week behavior
In the final 7 days, Home should begin surfacing more Live-oriented awareness:
final messages scheduled 
key vendors confirmed 
guest logistics nearing completion 
“Live mode activates soon” tone

8. Live Page — CTO Specification
Purpose
Live should be the wedding week and wedding day reassurance / coordination layer. It must add value before and on the day, not sit as dead weight.
There should effectively be two modes:
calm couple / bride-facing view 
operational planner-facing logic underneath or via privileged mode 
Bride-facing principle
The bride should not see stressful operational details. The bride-facing layer should only expose:
calm status 
what is happening now 
what is next 
quiet confirmations 
relevant updates 
weather if helpful 
support team access 
Planner-facing logic
The backend operational layer may track:
guest arrivals 
transportation exceptions 
delays 
vendor updates 
readiness checks 
manual confirmations from ushers / planners 
Before the wedding
In the final days, Live should act as:
countdown + coordination layer 
scheduled communications checkpoint 
logistics awareness surface 
final week readiness guide 
preview of what guests will experience in live mode 
Wedding day
Live should act as:
real-time event reassurance 
announcement layer 
timeline awareness 
update broadcaster 
calm interface for current and next moment 
Important realism constraint
The system should not pretend it knows things it cannot know. For example, it should not claim “everyone is seated” unless that is based on manual or check-in logic. Use:
estimated arrivals 
section confirmed 
family seated confirmed 
wedding party assembledrather than fake precision. 
What Live should integrate
schedule from Plan 
guest visibility from Guest Experience 
live update broadcasting from Messages / Guest Experience 
logistics status from Guest Logistics 
map / transport / weather as lightweight tools 
photo / gallery moment prompts if desired 
What it should not do
full guest database management 
full task planning 
deep invitation editing

11. Cross-Page Interaction Logic
This section is critical. The app will only feel coherent if these connections are implemented properly.
Home ↔ Plan
Home summarizes Plan but does not edit it.
Home ↔ Guests
Home shows guest completion and links into filtered Guest or Logistics states.
Plan ↔ Guests
Plan owns seating and event schedule. Guests consumes seating status and schedule visibility.
Plan ↔ Live
Live uses the event timeline from Plan.
Guests ↔ Invitations
Invitations use guest records and recipient segmentation from Guests.
Guests ↔ Guest Experience
Guest Experience renders content based on guest record, segment, and status.
Guests ↔ Messages
Messages target guest segments, missing states, and logistics needs.
Guests ↔ Logistics
Guest travel records, accommodation, and transport status feed Guest Logistics.
Guest Experience ↔ Live
Live updates can be surfaced inside the guest-facing experience.
Invitations ↔ Guest Experience
Invitation link should open into the guest-facing wedding experience.
Messages ↔ Live
A message may be sent as a live update, which appears as a popup or feed item in the guest-facing experience.
Gallery ↔ Guest Experience
Guest Experience can show gallery or upload prompts if enabled.
Registry ↔ Invitations / Guest Experience / Messages
Registry link can be included in invitations, shown in guest experience, and surfaced in reminder templates.
Registry ↔ Post-wedding Flow
Thank-you tracking becomes relevant after the event and may surface on Home or in a post-wedding checklist if desired.
12. Suggested Technical Pattern
Frontend
A modular mobile app for admin users, likely Flutter or React Native / native depending stack.
Guest link
A responsive web experience rendered from guest-specific state.
Backend
Role-aware API layer with:
wedding-scoped data 
guest-scoped access tokens for personalized link rendering 
modular services for messaging, invitations, uploads, registry, and logistics 
Data access pattern
Prefer:
normalized backend models 
denormalized summary objects / computed views for Home, Overview, Live, and analytics pages 
Event-driven logic
Use internal triggers for:
reminder suggestions 
progress updates 
live update propagation 
thank-you reminders 
invitation tracking updates 
Security
Guests should access a personalized, permission-scoped link. Collaborators should require authenticated app access with role permissions.
13. App Store / Play Store Readiness Considerations
For release readiness, the CTO should ensure:
robust guest link rendering on mobile web 
smooth deep-link handling from invitation channels 
proper notification permissions for collaborators and possibly couple/planner 
image upload handling with moderation queues 
resilient offline/loading states 
clean auth and onboarding for admins 
privacy-safe handling of guest contact data 
responsive UI that matches Figma exactly enough to preserve trust 
The user experience must feel polished enough that the user believes the product can carry emotional and operational weight. That means transitions, loading states, confirmations, and empty states matter.
